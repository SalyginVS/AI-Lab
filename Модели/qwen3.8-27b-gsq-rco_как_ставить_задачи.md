# Qwen3.8-27B GSQ-RCO в Pi: как ставить задачи

Назначение: правила постановки задач для архитекторов и исполнителей (Claude, ChatGPT), которые передают работу модели `qwen3.8-27b-gsq-rco:iq3s-mtp-262k` через Pi.
Основание: программа Q27 (E0–E1C, 2026-10-17…21), 12 прогонов на трёх задачах стека Node.js / PostgreSQL / React со скрытыми проверками; журналы Pi разобраны по каждому шагу.
Роль модели: локальный исполнитель сложных задач **по готовому проекту** (DESIGN). Проектирование, выбор архитектуры и приёмку она не выполняет.

## 1. Главное правило

Качество работы этой модели определяется в первую очередь точностью задания.
На одних и тех же задачах, с той же моделью и теми же настройками:

| Постановка | B4 (сервер + PostgreSQL) | C (React) |
|---|---|---|
| Только DESIGN | 98 %, нарушение правил размещения файлов | 96–98 %, нарушение правил размещения файлов |
| DESIGN + дополнение с явными правилами (раздел 3) | **100 %, без нарушений**, быстрее на 15–40 % | **100 %, без нарушений**, быстрее на 30 % |

## 2. Обязательные настройки

| Параметр | Значение | Почему |
|---|---|---|
| Глубина рассуждений | `medium` | `xhigh`: модель обдумывает весь проект 30+ минут до первого действия; `low`: не быстрее на React и даёт ошибки в сложной логике |
| Лимит ответа `maxTokens` | 262144 | рекомендация производителя; при 32768 ответ обрывался посреди рассуждений |
| Сэмплинг | temperature 1.0, top_p 0.95, top_k 20, min_p 0, presence_penalty 0 | рекомендация производителя для режима рассуждений |
| Контекст | 262144 | модель целиком в VRAM RTX 3090 |
| GPU | постоянный лимит 300 Вт; на карте одна модель | при 420 Вт аппаратный перегрев; Q27 и Q6 вместе не помещаются |

## 3. Шаблон задания

Задание = DESIGN (что сделать) + дополнение (как работать). Дополнение добавляется отдельным разделом в конце.

```markdown
## Правила работы над этой задачей

1. Где класть тесты. Новые тесты только здесь: <шаблон пути>.
   Можно: <пример 1>, <пример 2>. Нельзя: <запрещённые места>.
   Временные файлы удали перед сдачей. Перед сдачей проверь, что в diff нет файлов вне разрешённых путей.

2. Граничные случаи. Для каждого пункта должен существовать код, который его обрабатывает:
   - <случай> → <точный ожидаемый результат: код, текст, поведение>
   - ...

3. Самопроверка. Работающий код не переписывай без причины. Меняешь код — сначала покажи падающий тест,
   который это изменение исправляет. После правок повтори все проверки проекта.

4. Сдача. Перечисли выполненные команды проверки и их фактический результат.
```

## 4. Правила постановки (с основаниями)

1. **Всегда указывать место для тестов и пример имени файла.** Модель всегда пишет тесты сама и запускает их десятки раз. Если место не задано или шаблон неочевиден (`task-handoff.*.test.ts`), она кладёт тесты по своей привычке (`task-handoff.test.ts`, `test/…`). В задаче, где место было задано естественным шаблоном (`test/v2-*.test.ts`), она соблюдала его 2 раза из 2.
2. **Пограничные случаи списком, с ожидаемым результатом.** Из длинного описания модель извлекает их ненадёжно: в разных прогонах пропускает разные. Из списка извлекает все.
3. **Повторы при временных ошибках и конфликтах базы расписывать подробно.** Это устойчивое слабое место: повтор транзакции при 40P01/40001 и ответ 503 после исчерпания попыток пропущены в 4 из 6 прогонов, где они требовались. Указывать: какие коды, сколько попыток, что вернуть, и что код ошибки PostgreSQL может лежать во вложенной причине (обёртка ORM).
4. **В React расписывать асинхронные тонкости поимённо**: повторная отправка формы до перерисовки (нужна синхронная защита, а не только `disabled`), отмена запроса при закрытии экрана, игнорирование поздних ответов, ошибки сервера по полям.
5. **Если что-то запрещено, указывать код ответа.** Иначе модель выбирает правдоподобный вариант сама (например, 403 вместо ожидаемого 409).
6. **Самопроверку ограничивать.** Без ограничения она однажды превратила черновик 49/49 в 47/49. Общая команда «проверь всё» полезна мало: в 6 прогонах улучшила результат 1 раз.
7. **Не давать проектных решений на выбор.** Модель сильна в исполнении готового проекта и слабее там, где проект молчит.
8. **Замечания для доработки писать конкретно**: что ожидалось, что получено, как воспроизвести. Короткое «нарушен пункт X» она не исправляет (логические дефекты не исправлены 2 из 2 при кратких замечаниях).

## 5. Чего ожидать

| Показатель | Наблюдение |
|---|---|
| Время | средняя задача 35–60 мин, крупная 1,5–4,7 ч; разброс в основном от долгой отладки собственных тестов на конкурентность |
| Долгие паузы | до 30 минут рассуждений без действий — норма, это не зависание |
| Скорость | 25–40 токенов/с генерации, 830–1200 токенов/с чтения (300 Вт) |
| Честность отчётов | 41 подтверждённое утверждение и 1 ложное «всё зелёное» из 77 проверенных |
| Температура GPU | до 80 °C при 300 Вт |

## 6. Приёмка результата

Отчёт модели не является доказательством. Проверять внешними тестами: публичные проверки проекта, тесты приёмщика по пограничным случаям, diff на соответствие разрешённым путям.

## 7. Чего не делать

- Не включать `xhigh` и не ставить лимит ответа 32768.
- Не запускать Q27 одновременно с Q6 или другой большой моделью.
- Не давать задач без DESIGN («придумай и сделай»).
- Не принимать работу по тексту отчёта модели.
