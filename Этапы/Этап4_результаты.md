## Что сделано

### Классификация ошибок Ollama

Функция `classify_ollama_error()` парсит тело ответа Ollama и маппит HTTP-коды:

| Ошибка Ollama | HTTP-код клиенту | error.type | error.code |
|---|---|---|---|
| Модель не найдена (404) | 404 | not_found_error | model_not_found |
| Невалидный запрос (400) | 400 | invalid_request_error | bad_request |
| OOM (любой код + паттерн) | 503 + Retry-After: 30 | server_error | oom |
| Внутренняя ошибка (5xx) | 502 | server_error | ollama_error |
| Прочие коды | проксируется | api_error | {код} |

Раньше: любая ошибка → 502 с `{"detail": "..."}`. Теперь: правильный код + формат OpenAI.

### OOM-детекция

8 паттернов для обнаружения ошибок нехватки памяти (GPU/RAM): "out of memory", "cuda out of memory", "failed to allocate" и др. Case-insensitive. При OOM — HTTP 503 с заголовком `Retry-After: 30` и рекомендацией уменьшить модель или num_ctx.

### Retry при холодном старте

`ollama_post_with_retry()` — обёртка над client.post с retry:

| Параметр | Значение | Обоснование |
|---|---|---|
| Попытки | 3 (1 + 2 retry) | Холодный старт 35B ~ 8-30 сек |
| Backoff | 2с → 4с (экспоненциальный) | Суммарно ~6с паузы |
| Retry при | httpx.RequestError | Сетевые ошибки (connection reset, timeout) |
| НЕ retry при | httpx.HTTPStatusError | Ollama ответила кодом — классифицируем |

После провала всех попыток — быстрая проверка Ollama (GET /api/tags, timeout 5с):
- Ollama жива → 503 "Model is loading into GPU memory (cold start)"
- Ollama мертва → 502 "Cannot connect to Ollama"

### OpenAI-совместимый формат ошибок

Все ошибки шлюза теперь в формате OpenAI API:
```json
{"error": {"message": "...", "type": "...", "code": "..."}}
```

Три exception handler'а:
- `GatewayError` → OpenAI-формат (основные ошибки шлюза)
- `HTTPException` → OpenAI-формат (стандартные FastAPI ошибки)
- `RequestValidationError` → OpenAI-формат (Pydantic 422, первоначально пропущен — FastAPI отдавал `{"detail": [...]}` вместо `{"error": {...}}`, исправлено по результатам тестирования)

### Фикс логгера

`logging.getLogger("llm-gateway")` → `logging.getLogger("uvicorn.error")`. Синхронизация кода в проекте с тем, что работает на сервере (баг обнаружен на Этапе 3, но в файле проекта не был исправлён).

## Исправленный баг в ходе тестирования

**RequestValidationError не перехватывался.** Pydantic validation errors в FastAPI проходят через `RequestValidationError` (отдельный класс), а не через `HTTPException`. Первоначальная версия v0.4.0 имела handler только для `HTTPException`, из-за чего 422 ответы приходили в стандартном FastAPI-формате `{"detail": [...]}` вместо OpenAI-формата `{"error": {...}}`. Исправлено добавлением `from fastapi.exceptions import RequestValidationError` и отдельного handler'а `validation_error_handler`.
