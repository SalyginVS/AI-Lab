## Transaction scope
Server: four new files (97 boot drop-in, 95 readiness drop-in, readiness script, tmpfiles rule) and the four managed boot links. Existing power service, guards, legacy postboot, profiles, and switcher remain unchanged. The links implement the target-host systemd enablement observed in E03-P; any differing layout or state is refused. On live apply, daemon-reload and systemd-analyze verify do not start units. Readiness is read-only; READY_PENDING_FUNCTIONAL is not functional PASS. Client: only models.json and settings.json, addresswise delta from pi-config-intent.json. The private input file hashes must match the independent review. Ollama, global max, unrelated provider/settings fields, auth and session history are not modified. Stop/close Pi and IDE sessions before applying.

Both transactions persist a mode-0700 private backup with transaction.json (PREPARED before first mutation, INSTALLED / ROLLED_BACK / RECOVERY_REQUIRED). The backup stores original bytes, permission bits and owner/group for managed objects, original symlink targets, and expected replacements. Keep backup outside the repository; never publish it. Per-object atomic replacement and fsync are used; the transaction is recoverable, not an atomic multi-file kernel operation. If interrupted, inspect the journal and use rollback, not a new install. Rollback verifies every managed object is the original or expected replacement before restoring in reverse order. Third-party edits or extra files in new directories cause refusal; no blanket restore. File metadata scope is content, mode, uid/gid and link target, not filesystem timestamps or arbitrary ACL/xattrs. Actual live privileged transaction and post-reboot rollback remain NOT_RUN.
