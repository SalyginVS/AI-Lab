## Что сделано

### Шаг 0 — Аудит сервера

Исходное состояние: Ollama 0.17.4, 9 моделей, 761 ГБ свободно на SSD. qwen3.5:35b — архитектура qwen35moe (MoE, 36B параметров), контекст 262144, Q4_K_M. Re-pull не требовался по архитектуре, но потребовался для фиксов penalties (Шаг 1).

### Шаг 1 — Upgrade Ollama 0.17.4 → 0.18.0

Перепрыгнули 4 промежуточных релиза (0.17.5–0.17.8). Ключевые фиксы, вошедшие в обновление:

| Версия | Фикс | Влияние на наш стек |
|--------|-------|---------------------|
| 0.17.5 | Краш qwen3.5 при GPU+CPU offload | Наша конфигурация Depth over Speed |
| 0.17.5 | Penalties (repeat/presence/frequency) игнорировались Go runner'ом | Шлюз передавал, Ollama отбрасывала |
| 0.17.5 | qwen3.5 бесконечные повторы из-за отсутствия presence penalty | Требует re-pull модели |
| 0.17.6 | Tool calling qwen3.5 — неправильный parser pipeline (Hermes JSON вместо Qwen-Coder XML) | Объясняет «мусор» на Этапе 7A |
| 0.17.7 | reasoning_effort в OpenAI-совместимом API | Потенциальный конфликт с нашим маппингом |
| 0.17.7 | qwen3-coder raw mode в /api/generate | Затрагивает autocomplete через FIM |
| 0.18.0 | Облачные модели, OpenClaw | Для нас нерелевантно (всё локально) |

**Re-pull qwen3.5:35b** выполнен. Проверка: ответ "Four" на "2+2" без зацикливания, presence_penalty=1.5 реально применяется, thinking работает (5079 chars), краша при GPU+CPU offload нет.

**Решение по reasoning_effort:** оставляем вариант A — собственная логика think на стороне шлюза. reasoning_effort НЕ передаётся в payload Ollama (шлюз резолвит effort через resolve_effort() и маппит только на think: true/false). Причины: наш шлюз фильтрует thinking из content, разделяет usage на completion_tokens и reasoning_tokens, управляет reasoning_content. Ollama с 0.17.7 понимает reasoning_effort, но не обеспечивает эту обработку. Пересмотр — когда Ollama добавит гранулярные уровни thinking.

### Шаг 2 — FIM-модели для autocomplete

Скачаны:
- **qwen2.5-coder:7b** (4.7 ГБ) — основная FIM-модель для tab-completion
- **qwen2.5-coder:1.5b** (986 МБ) — fallback (если 7b мешает по памяти)

**Ключевое знание:** autocomplete в Continue.dev = FIM (Fill-in-the-Middle), не chat completions. FIM использует специальные токены (`<|fim_prefix|>`, `<|fim_suffix|>`, `<|fim_middle|>`). Chat-модели не обучены этому формату и не подходят для autocomplete. Continue отправляет FIM-запросы через Ollama `/api/generate` напрямую (provider: ollama), минуя шлюз gateway.py.

### Шаг 3 — qwen3.5:9b

Скачана qwen3.5:9b (6.6 ГБ). Dense-архитектура (qwen35, не MoE как у 35b), 9.7B параметров, capabilities: completion, vision, tools, thinking. Роль: быстрый повседневный чат вместо тяжёлой qwen3.5:35b.

### Шаг 4 — OLLAMA_MAX_LOADED_MODELS=2

Изменён systemd override: `OLLAMA_MAX_LOADED_MODELS=1 → 2`. Позволяет держать FIM-модель резидентной параллельно с chat/agent моделью. Устраняет холодный старт при переключении между autocomplete и chat. Суммарная память 86 ГБ позволяет любую пару моделей.

Актуальный override `/etc/systemd/system/ollama.service.d/override.conf`:

```ini
[Service]
Environment="OLLAMA_FLASH_ATTENTION=1"
Environment="OLLAMA_KV_CACHE_TYPE=q8_0"
Environment="OLLAMA_MAX_LOADED_MODELS=2"
Environment="OLLAMA_HOST=0.0.0.0:11434"
Environment="CUDA_VISIBLE_DEVICES=0"
Environment="GGML_CUDA_NO_GRAPHS=1"
```

## Обнаруженные проблемы и решения

### 1. tabAutocompleteModel не существует в YAML-формате (КРИТИЧНО)

**Симптом:** `No autocomplete model configured and provided model not found in config`

**Причина:** в YAML-формате Continue (schema v1) нет top-level ключа `tabAutocompleteModel`. Это синтаксис старого config.json. В YAML все модели (chat, autocomplete, embed) — внутри массива `models`, роль определяется полем `roles: [autocomplete]`.

**Решение:** модель с `roles: [autocomplete]` внутри `models`, настройки в `autocompleteOptions` на уровне модели.

### 2. Таймаут autocomplete при холодном старте (КРИТИЧНО)

**Симптом:** `The operation was aborted` в логах Continue при попытке FIM-запроса к Ollama.

**Причина:** дефолтный таймаут autocomplete в Continue ~5 секунд. Первый запрос к qwen2.5-coder:7b — холодный старт (загрузка 4.7 ГБ в VRAM), занимает 5-15 секунд. Continue отменяет запрос.

**Решение:** `requestOptions.timeout: 30000` + `autocompleteOptions.modelTimeout: 30000` (30 секунд). Влияет только на холодный старт, после загрузки модели запросы <1 сек.

### 3. qwen3-coder Apply не сработал в Agent mode (НИЗКО)

**Симптом:** ✕ на "Continue tried to edit fibonacci.py" и "Agent tool use" при работе qwen3-coder в Agent mode.

**Причина:** модель генерировала diff для редактирования существующего файла (созданного glm-flash), Continue не смог наложить diff. Не баг шлюза — tool_calls приходят корректно (подтверждено curl).

**Статус:** не блокирует. Относится к Этапу 7C (Agent + Context Providers). glm-flash создавала файл с нуля — работала без ошибок.

## Грабли Continue 1.2.17 (дополнение к Этапу 7A)

- **tabAutocompleteModel** (top-level) — НЕ работает в YAML schema v1. Модель autocomplete — внутри `models` с `roles: [autocomplete]`
- **autocompleteOptions** — внутри определения модели, не top-level
- **debounce → debounceDelay** — правильное имя параметра в YAML-схеме
- **disableInFiles** — настройка VS Code UI (Settings), не config.yaml
- **Дефолтный таймаут autocomplete ~5 сек** — слишком мало для холодного старта. Нужен `requestOptions.timeout: 30000` + `autocompleteOptions.modelTimeout: 30000`
- **Autocomplete-модель не видна в дропдауне** — нормально (роль только `autocomplete`, без `chat`)
