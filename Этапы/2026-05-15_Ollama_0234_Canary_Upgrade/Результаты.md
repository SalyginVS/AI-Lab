# Результаты: Ollama 0.23.4 canary upgrade

**Дата:** 2026-05-15  
**Стенд:** AI Lab RTX 3090  
**Сервер runtime:** `llm` / `192.168.0.128`  
**Source-of-truth документации:** `/home/vladimir/llm/AI-Lab`  
**Итоговое решение:** `OLLAMA_0234_CANARY_ACCEPTED_WITH_MINOR_EVIDENCE_GAP`

---

## 1. Контекст

Целью работы было проверить upgrade Ollama runtime с фактической версии `0.22.1` до `0.23.4` как консервативный canary перед переходом на более свежие ветки.

Проектная документация частично содержала устаревшее указание `Ollama 0.20.7`, но baseline на сервере показал фактический runtime `0.22.1`.

---

## 2. Baseline до upgrade

Подтверждено перед изменениями:

- `ollama.service`: `enabled`, `active`;
- gateway `/health`: `ok`;
- gateway version: `0.12.0`;
- gateway `models_count=14`, `pipelines_count=6`;
- `health-check`: `10/11`, единственный fail - старый drift `Ollama model count = 12`;
- системные override-переменные Ollama сохранены:
  - `OLLAMA_FLASH_ATTENTION=1`;
  - `OLLAMA_KV_CACHE_TYPE=q8_0`;
  - `OLLAMA_NUM_PARALLEL=1`;
  - `GGML_CUDA_NO_GRAPHS=1`;
  - `OLLAMA_CONTEXT_LENGTH=131072`.

---

## 3. Инцидент при установке

Попытка установки через официальный `install.sh` с `OLLAMA_VERSION=0.23.4` была прервана во время скачивания/распаковки:

```text
curl: HTTP/2 stream ... PROTOCOL_ERROR
Unexpected EOF in archive
```

После этого:

- binary показывал `0.23.4`, но runtime был повреждён;
- возникали состояния `Permission denied` / `Segmentation fault`;
- `ollama.service` уходил в restart loop;
- первоначально были признаки CPU-only или некорректного GPU discovery.

Вывод: pipe-installer / streaming download нельзя считать безопасным repair-механизмом при нестабильной сети и больших release artifacts.

---

## 4. Восстановление

Рабочий recovery path:

1. Остановить `ollama.service`.
2. Скачать полный release artifact напрямую через `aria2c`.
3. Проверить архив:
   - `zstd -t`;
   - `tar -I zstd -tf`.
4. Сделать backup повреждённого runtime.
5. Удалить повреждённый `/usr/local/lib/ollama`.
6. Распаковать архив вручную:
   - `sudo tar -I zstd -xpf ollama-linux-amd64.tar.zst -C /usr/local`.
7. Восстановить права:
   - `sudo chown root:root /usr/local/bin/ollama`;
   - `sudo chmod 755 /usr/local/bin/ollama`.
8. Перезапустить `ollama.service`.

---

Подтверждено:

- `/api/version`: `0.23.4`;
- `ollama.service`: `active`;

- `qwen3.5:9b` загружался как `100% GPU`;
- `qwen3-embedding` загружался как `100% GPU`;
- `qwen2.5-coder:7b` загружался как `100% GPU`;
- gateway после рестарта: `active`;
- gateway `/health`: `ok`;
- embeddings endpoint: `OK`, `embedding_dim=4096`;
- `health-check`: снова `10/11`, единственный fail - старый model-count drift.

---

## 6. Minor evidence gap

Финальный gateway chat smoke был запущен с корректным JSON-parsing токена. Последующие `ollama ps` показывали `qwen2.5-coder:7b` как `100% GPU`, что соответствует выбранной модели gateway chat smoke.

Однако финальная строка structured gateway log вида `llm_completion status_code=200` не была вставлена в диалог. Поэтому формальный evidence status:

```text
GATEWAY_CHAT_RUNTIME_PATH=confirmed_by_model_load
GATEWAY_CHAT_STRUCTURED_LOG_EVIDENCE=not_pasted
BLOCKER=no
```

Решение: gap не блокирует acceptance, но фиксируется честно.

---
