## 6. Qwen3.8 Flash-Next Q6 runtime profile

### 6.1. Model-scoped runner

Q6 использует model-scoped wrapper:

```text
/usr/local/lib/ollama/llama-server
/usr/local/lib/ollama/llama-server.real-0.35.1
```

Текущий Q6 model ID:

```text
09b8aff72a79
```

Accepted profile:

```text
N_CPU_MOE=43
per_layer_token_embd=CPU
lazy=on
load=mmap
threads=8
batch=512
ubatch=512
MTP/speculative=off
KV=q8_0
Flash Attention=on
```

Wrapper должен применять профиль только к Q6. Q5 и другие модели не должны наследовать Q6-specific CPU-MoE/PLE overrides.

### 6.2. Performance acceptance

Accepted measured profile:

```text
realistic 8K prefill  ~35.05 tok/s
DECODE_A               ~9.713 tok/s
```

Короткие smoke-run decode значения не переопределяют этот baseline.

Rejected alternatives:

```text
cpu_moe=42  -> decode ~9.407 tok/s
threads=16  -> decode ~8.816 tok/s
```

### 6.3. Upgrade caveat

Ollama runtime upgrade/replacement может заменить `/usr/local/lib/ollama/llama-server`.

После обновления Ollama обязательно:

1. проверить runner wrapper;
2. при необходимости переустановить wrapper;
3. подтвердить Q6 model-scoped activation;
4. подтвердить Q5 isolation;
5. выполнить runtime smoke.

## 12. Mandatory execution contract для Q6

Серьёзная Q6-задача не задаётся свободным conversational prompt.

Стандарт:

```text
confirmed project evidence
-> TASK.md + spec/*
-> explicit final result
-> baseline + source-of-truth
-> allowed scope
-> forbidden changes
-> invariants
-> acceptance gates
-> bounded execution
-> first-pass checkpoint
-> mandatory full self-review
-> regression tests for real findings
-> root-cause repair
-> full gate rerun
-> final diff review
-> READY_FOR_REVIEW
-> independent acceptance
```

Дополнительные правила:

- уже принятые архитектурные решения не перепроектируются исполнителем;
- модели оставляется свобода внутренних инженерных решений внутри scope;
- не задавать ожидаемое количество дефектов;
- зелёные tests первой реализации не означают завершение;
- model final status = `READY_FOR_REVIEW`;
- внешний control/review plane выдаёт `ACCEPTED`.

При harness failure:

1. не начинать реализацию заново;
2. сохранить workspace/checkpoint;
3. исправить execution environment;
4. продолжить из фактического состояния;
5. first-pass evidence не перезаписывать.
