# Qwen3.8-27B простыми словами: как пользоваться

Для Владимира. Короткое руководство с примерами.

## Что это за модель и зачем она

Это **локальный программист-исполнитель**. Он работает на нашем сервере с видеокартой RTX 3090, без интернета и без платы за запросы.

Его сильная сторона: **сделать готовый проект**. Если подробно описано, что нужно построить (какие функции, какие ошибки, какие ответы), он напишет код, тесты и сам всё проверит. На наших испытаниях при хорошем описании он сделал две реальные задачи на 100 %.

Его слабая сторона: **думать за вас там, где описание молчит**. Если в задании не сказано, что делать в каком-то случае, он выберет вариант сам, и не всегда тот, что нужен.

Аналогия: это сильный исполнитель, которому нужно хорошее техническое задание. Хорошее ТЗ даёт отличный результат, расплывчатое — посредственный.

## Как запустить

1. Включите сервер лаборатории.
2. На ноутбуке Dell откройте терминал (**Ctrl + Alt + T**).
3. Перейдите в папку проекта, где нужно работать, например:
   ```
   cd ~/projects/my-app
   ```
4. Запустите модель командой:
   ```
   pi-q27
   ```
   Это короткая команда, которая включает нужные настройки: средняя глубина рассуждений, правильные лимиты.
5. Вставьте задание (как его писать, ниже) и нажмите Enter.

Первый ответ может прийти через 1–2 минуты: модель загружается в видеокарту. Если до этого работала Q6, она будет выгружена автоматически, две большие модели одновременно не помещаются.

## Как писать задание

Задание состоит из двух частей:
1. **Что сделать.** Описание проекта: функции, данные, ответы, ошибки.
2. **Правила работы.** Куда класть тесты, какие особые случаи обработать, как проверить.

### Пример: плохое задание

> Сделай в моём Node.js приложении API для заявок на ремонт с PostgreSQL.

Что будет: модель сама решит, какие поля, какие ошибки, куда положить тесты. Получится работающий, но «чужой» код, который придётся долго переделывать.

### Пример: хорошее задание

```markdown
## Задача
В приложении (Node.js, Hono, PostgreSQL, Drizzle) добавить API заявок на ремонт.

Таблица repair_requests: id (uuid), title (текст 3..120), status ('open'|'done'), created_at.
Новый файл: src/routes/repair.ts, подключить в src/app.ts.

Endpoints:
- POST /api/repairs {title} → 201 {request}
- GET /api/repairs/:id → 200 {request}
- POST /api/repairs/:id/done → 200 {request}

## Правила работы над этой задачей
1. Где класть тесты: только src/routes/repair.<что-то>.test.ts,
   например src/routes/repair.api.test.ts. Временные файлы удали перед сдачей.
2. Особые случаи (каждый должен быть обработан в коде):
   - title короче 3 или длиннее 120 символов → 422 {error:'Validation failed'}
   - заявка не найдена → 404 {error:'Not found'}
   - повторное done для закрытой заявки → 409 {error:'Already done'}
   - невалидный JSON в теле → 400 {error:'Invalid JSON body'}
   - конфликт базы (коды 40P01, 40001): повторить транзакцию до 3 раз,
     потом 503 {error:'Temporary database conflict'};
     код ошибки PostgreSQL может лежать во вложенной ошибке (cause)
3. Самопроверка: не переписывай работающий код без падающего теста.
4. В конце перечисли команды проверки, которые ты запускал, и их результат.
```

Что будет: модель сделает именно это, положит тесты куда сказано и обработает все перечисленные случаи.

### Пример для React

```markdown
## Правила работы над этой задачей
1. Тесты только в src/feedback/, например src/feedback/form.test.tsx. Папку test/ не трогать.
2. Особые случаи формы:
   - пока идёт отправка, второе нажатие «Отправить» не отправляет повторно
     (защита должна срабатывать сразу, одного disabled у кнопки мало)
   - если пользователь закрыл экран во время отправки, запрос отменяется,
     поздний ответ ничего не меняет
   - ошибки сервера по полям показываются у своих полей, общий текст в role='alert'
```

## Чего ожидать во время работы

- **Долгие паузы до 30 минут без видимых действий — это нормально.** Модель обдумывает решение, а не зависла.
- **Время:** небольшая задача 30–60 минут, крупная 1,5–5 часов.
- **Модель сама запускает тесты** десятки раз, видит ошибки и чинит их.
- **Видеокарта** греется до 80 °C, это в норме при лимите 300 Вт.

## Как проверить результат

Не верьте на слово отчёту «всё готово, все тесты зелёные». Обычно это правда, но не всегда (на испытаниях 1 случай из 77). Проверка:

1. Сами запустите тесты проекта, например `npm test`.
2. Посмотрите, какие файлы изменены (`git status`): нет ли лишних файлов не там, где разрешено.
3. Важные особые случаи проверьте отдельно: попросите Claude или ChatGPT написать на них тесты, либо проверьте сами.

## Если что-то не так

| Что видите | Что это | Что делать |
|---|---|---|
| Нет ответа 5–30 минут | модель думает | ждать |
| Долго нет новых сообщений | не обязательно зависание: Q27 может думать десятки минут, молчание само по себе ничего не доказывает (Грабли 090) | Не прерывайте по времени. Проверьте: программа Pi на Dell работает; на сервере модель загружена и карта занята (`ssh llm 'ollama ps'`, свежий `nvidia-smi`); в папке проекта появляются изменения (`git status --short`). Если что-то из этого живое, ждите. Если состояние неясно, сначала разберитесь, а не запускайте заново: повторный запуск того же задания может продублировать уже сделанное. После подтверждённого обрыва восстанавливайте работу по `git status` и сохранённым результатам, а не с нуля. Подробности в методике v1.1 |
| Сделала не то в каком-то случае | случай не был описан | дописать его в «Особые случаи» и попросить исправить, с примером «что ожидалось, что получилось» |
| Положила файлы не туда | не было явного правила | указать место для тестов с примером имени |
| Медленно начинает работу | загружается в видеокарту после Q6 | подождать 1–2 минуты |

## Когда брать Q27, а когда другую модель

- **Q27:** реализовать готовый, подробно описанный проект на Node.js, PostgreSQL, React. Тесты, исправления по конкретным замечаниям.
- **Не Q27:** придумать архитектуру, выбрать подход, разобраться в размытой задаче. Это работа Claude или ChatGPT. Они готовят задание, Q27 исполняет, они же принимают результат.

## Чего не делать

- Не переключать глубину рассуждений на максимальную (`/thinking` → xhigh): модель будет думать бесконечно долго.
- Не запускать одновременно Q27 и Q6.
- Не давать задачу без описания («сделай что-нибудь хорошее»).
