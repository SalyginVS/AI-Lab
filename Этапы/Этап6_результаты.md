## Что сделано

### Настоящий стриминг (Этап 6)

**Проблема:** `httpx.AsyncClient.post()` буферизует весь ответ Ollama в память. `resp.aiter_lines()` итерирует по уже загруженному буферу. TTFT (Time To First Token) = полному времени генерации. Для 35B модели — минуты ожидания до первого символа.

**Решение:** новая функция `ollama_stream_with_retry()` использует паттерн «ручной streaming mode» из документации httpx:

1. `client.build_request("POST", url, json=payload)` — создаёт HTTP-запрос
2. `client.send(req, stream=True)` — отправляет запрос, возвращает response сразу после получения HTTP headers (body НЕ читается)
3. При HTTP ≠ 200: `await resp.aread()` + `await resp.aclose()` + классификация ошибки (существующая `classify_ollama_error()`)
4. При HTTP 200: возвращает открытый response — `stream_generator()` читает body через `resp.aiter_lines()` по мере поступления данных от Ollama
5. `StreamingResponse(..., background=BackgroundTask(resp.aclose))` — гарантирует закрытие httpx response после завершения генератора (и при нормальном выходе, и при обрыве клиента)

**Retry-логика:** идентична Этапу 4 — retry при `httpx.RequestError` (connection errors), не retry при HTTP-ошибках. Retry возможен только на фазе установления соединения (до начала получения данных). Mid-stream retry невозможен и не нужен.

**Non-stream path:** без изменений, по-прежнему использует `ollama_post_with_retry()` с буферизованным `client.post()`.

### Объём изменений

- Новый import: `from starlette.background import BackgroundTask`
- Новая функция: `ollama_stream_with_retry()` (~40 строк)
- Изменение в `chat_completions()`: stream path использует новую функцию + BackgroundTask
