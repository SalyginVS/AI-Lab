# Приёмочный набор RB-10

Статус: ACCEPTED RB-10, 2026-10-17.
Порядок: T-FAST, оценка, затем разрешённый T-MED. T-LONG требует отдельного решения владельца.

## Источники и неизменность ожиданий

`tests/acceptance/baseline.json` содержит пары `value` / `source` для каждого ожидания. Источником являются акты, артефакты и ADR программы.
Baseline зафиксирован отдельным commit до первого прогона. Его commit и SHA256 находятся в поставке, в `baseline-commit.json` и `first-run.json`.
Изменение baseline для устранения расхождения с живой системой запрещено. Исправлять можно сборщик или оценщик при доказанном TEST_DEFECT.
Фиксированные строки embedding сохранены в `embedding_strings.json`. Их SHA256 включён в baseline до прогона.

## Когда запускать

T-FAST выполнять после каждого этапа сборки и после обновления. F07 выполнять после каждого включения сервера: сервер по умолчанию выключен, а обновления ставятся, пока он включён.
T-MED выполнять после завершения сборки и после обновления условий исполнения Q6, с разрешением владельца.
T-LONG выполнять по процедуре `tests/acceptance/t_long/PROCEDURE.md`, с отдельным разрешением. В RB-10 он не запускался.
Тест NVIDIA в контейнере относится к RB-14. Одобренный образ с digest выбирается при этом испытании. До него проверка открыта и не блокирует переход 10: проверяются nvidia-smi на хосте и зарегистрированный runtime NVIDIA. Загрузка образа в этапе RB-10 запрещена.

## Команды

Команды запускаются с Dell. `LAB_REBUILD_ROOT` задаёт отдельную рабочую копию, `LAB_EVIDENCE_DIR` задаёт каталог протоколов.
`LAB_SSH_TARGET` задаёт существующий SSH alias, а не адрес в публичной документации.

```bash
A="$LAB_REBUILD_ROOT/Сборка/tests/acceptance"
mkdir -p "$LAB_EVIDENCE_DIR/protocols"
ssh -T "$LAB_SSH_TARGET" 'bash -s' < "$A/t_fast_server.sh" > "$LAB_EVIDENCE_DIR/protocols/t_fast_server.json"
python3 -I "$A/t_fast_client.py" > "$LAB_EVIDENCE_DIR/protocols/t_fast_client.json"
python3 -I "$A/evaluate.py" --raw "$LAB_EVIDENCE_DIR/protocols/t_fast_server.json" --client "$LAB_EVIDENCE_DIR/protocols/t_fast_client.json" --output "$LAB_EVIDENCE_DIR/protocols/t_fast_server_evaluated.json"
python3 -I "$A/evaluate.py" --raw "$LAB_EVIDENCE_DIR/protocols/t_fast_client.json" --output "$LAB_EVIDENCE_DIR/protocols/t_fast_client_evaluated.json"
```

T-FAST сервера использует одну SSH-сессию и не загружает модели. Клиентский сборщик читает метаданные Pi и VS Code, не запускает npm, pi или code.
Приватные F08 и C05 исполняются по приватному приложению. Оно позволяет объединить их с T-FAST сервера в одной SSH-сессии.

```bash
python3 -I "$A/test_evaluate.py"
python3 -I "$A/t_med.py" --ssh-target "$LAB_SSH_TARGET" --output "$LAB_EVIDENCE_DIR/protocols" --private-output "$LAB_PRIVATE_EVIDENCE_DIR"
python3 -I "$A/evaluate.py" --raw "$LAB_EVIDENCE_DIR/protocols/t_med.json" --embedding-reference "$A/embedding_reference.rb10.json" --output "$LAB_EVIDENCE_DIR/protocols/t_med_evaluated.json"
```

На Dell проверено 2026-10-17: `python3 -I` импортирует pexpect из `/usr/lib/python3/dist-packages/pexpect/__init__.py`. Файл принадлежит системному пакету `python3-pexpect=4.9-4`; установленная зависимость `python3-ptyprocess=0.7.0-6build1`. На новом клиенте установить `python3-pexpect` из официального архива Ubuntu выбранной ОС, затем проверить импорт командой `python3 -I -c 'import pexpect; print(pexpect.__file__)'`. Системный пакет доступен в изолированном режиме; установка только в пользовательский site-packages его не заменяет.

Транспорт T-MED ожидает приглашение входа по паролю; это принятая настройка. Если на новой площадке вход по ключу, транспорт нужно доработать отдельной задачей. Не менять настройки SSH только ради теста.

`t_med.py` читает пароль SSH из стандартного ввода. Не помещайте пароль в команду, файл или журнал. Для интерактивного запуска введите его в строке ввода.
Pi запускается во временном HOME. Из живого профиля копируются settings.json и models.json. Если Pi требует credential провайдера, во временный auth.json копируется только запись выбранного провайдера. Значение в протокол не попадает. Выбирается Q6 явно, чтобы старый defaultModel не менял предмет проверки.
Временный каталог становится рабочим каталогом Pi. Внешние расширения, инструменты и обнаружение контекстных файлов отключены. Режим offline исключает стартовые обновления.
Токен для embedding читается внутри удалённой команды и не попадает в протокол.
Полные протоколы M10 и M11 сохраняются только в приватном приложении. Публичный протокол содержит номера и статусы проверок.

Каждый запрос Q6 ограничен 15 минутами. Весь T-MED ограничен 60 минутами. При недоступности Ollama выполнение останавливается без перезапуска сервиса.
Нельзя запускать несколько экземпляров T-MED одновременно. Параметр `--only M04` предназначен для ограниченного повторного прогона после исправления дефекта теста.
При повторе сохраняйте исходный протокол отдельно. Для M02/M03 требуется завершённый M01, для M06 требуется M05 в том же интервале наблюдения.

## Оценка

| Статус | Действие |
|---|---|
| PASS | Критерий подтверждён |
| FAIL | Записать нарушение функции или инварианта с сырым протоколом |
| DRIFT | Записать изменившуюся версию или хеш, не менять ожидание |
| REVALIDATE | Зафиксировать смену условий Q6 и согласовать ревалидацию по ADR-031 |
| TEST_DEFECT | Исправить только тест; повторить затронутую часть |
| INFO | Наблюдение без критерия приёмки |

Код выхода evaluate.py: 0 при отсутствии FAIL, REVALIDATE и TEST_DEFECT; 1 при FAIL или REVALIDATE; 2 при TEST_DEFECT.
Итог сохраняет все проверки, даже если у одного ID несколько статусов. Итоговый статус ID имеет приоритет TEST_DEFECT, FAIL, REVALIDATE, DRIFT, INFO, PASS.
Отсутствие строк профиля с загрузки системы отмечается INFO. Оно не доказывает изоляцию. Проверка M03 требует отдельного подтверждения строки в интервале запроса.
Первый F07 чистой установки сравнивает весь список установленных пакетов с `baseline.json`. Отличия пакетов вне lock ожидаются и разбираются: обычные отличия классифицируются DRIFT, изменения ядра, NVIDIA и Ollama требуют REVALIDATE. Смена Ollama дополнительно контролируется F01. После приёмки владельцем новая платформа получает свой вариант эталона по [80](80_Восстановление_и_апгрейд.md#смена-платформы).

F07 сопоставляет имена пакетов в формате принятого lock. Суффикс архитектуры нормализуется только при отсутствии коллизии нескольких архитектур.
Полный список отличий сохраняется. Новое установленное ядро требует REVALIDATE, даже если работающее ядро ещё не изменилось.
Смена ядра, NVIDIA, Ollama, runner или Q6 не подтверждается одним коротким ответом. По ADR-031 требуется согласованная ревалидация принятой роли Q6.

## Эталон embedding

Принятые байты RB-10 опубликованы в [embedding_reference.rb10.json](tests/acceptance/embedding_reference.rb10.json). SHA256: `c96188ba434a2c0762a6dd324f968500131f0341bee1a1aa25e7f21a9d60ecaa`; рядом лежит [файл контрольной суммы](tests/acceptance/embedding_reference.rb10.json.sha256). Файл скопирован байт в байт из принятого протокола. Перед оценкой проверить его: `(cd "$A" && sha256sum -c embedding_reference.rb10.json.sha256)`.
Точное совпадение первого ответа ожидается на той же GPU, драйвере и версии Ollama. На другом оборудовании расхождение означает новую платформу. Новый эталон принимает владелец по [80](80_Восстановление_и_апгрейд.md#смена-платформы), без подмены исходного файла. Повторные ответы на тот же текст сравниваются и описываются как INFO по RB-10.1. Новый прогон пишет отдельный embedding_reference.json; это не замена принятому embedding_reference.rb10.json.

`embedding_reference.json` сохраняет два набора векторов и SHA256 исходных строк. Индексы строк и порядок векторов проверяются.
Каждый вектор должен содержать 4096 конечных чисел. В исходном принятом эталоне допуск равен максимальному абсолютному расхождению двух прогонов,0. Новый измеренный comparison_atol из сырой пробы не заменяет принятый эталон автоматически.
Если расхождение равно нулю, требуется точное совпадение числовых значений. Автоматический запас допуска не добавляется.
M05 сравнивает первый ответ на те же строки с первым набором принятых векторов точно, atol=0. Для этого передайте evaluate.py параметр `--embedding-reference /absolute/accepted/embedding_reference.json`. Неизменный размер 4096 сам по себе не доказывает тождество embedding.

## F09 и эталон 2026-10-18: постоянный лимит GPU

Проверка `F09` в `t_fast_server.sh` выполняет **только чтение** `nvidia-smi power.limit`, `systemctl show` и `systemctl is-enabled`. Она не устанавливает лимит. Оценщик `evaluate.py` требует `power.limit=300` (погрешность представления менее 0.01 Вт), `ailab-gpu-power.service` в состоянии `active (exited)`, `Result=success`, `ExecMainStatus=0` и `enabled`. Иное значение или ошибочный код опроса дают FAIL.

[Новый live-эталон](tests/acceptance/baseline.live-2026-10-18.json) повторяет принятый `baseline.live-2026-10-17.json` с единственным добавлением: F09 и источники его ожиданий. Оба предыдущих baseline сохранены без изменений. Для исторических baseline, в которых нет F09, оценщик выставляет `INFO:historical_baseline_without_F09` вместо ложного `TEST_DEFECT`; такой прогон **не подтверждает** нынешнюю политику 300 Вт.

```bash
A="$LAB_REBUILD_ROOT/Сборка/tests/acceptance"
python3 -I "$A/evaluate.py" --baseline "$A/baseline.live-2026-10-18.json" --raw "$LAB_EVIDENCE_DIR/protocols/t_fast_server.json" --output "$LAB_EVIDENCE_DIR/protocols/t_fast_power_evaluated.json"
python3 -I "$A/test_evaluate.py"
```

Установщик postboot **для новых поставок** включает все три baseline и выбирает `baseline.live-2026-10-18.json` по умолчанию. Проверяются F01–F07 и F09. При необходимости историческую сборку проверяют явно через `--baseline-name baseline.json` либо `--baseline-name baseline.live-2026-10-17.json`, учитывая INFO вместо принятого F09. Действующая служба postboot на сервере остаётся со своей старой версией до **отдельно согласованного** развёртывания нового коммита по [50, раздел 10](50_Сервисы_Gateway_MCP.md#10-проверка-после-включения).

Принятое основание лимита: 420 Вт привели к `HW Thermal Slowdown` примерно через 5,5 минуты полной нагрузки; при 300 Вт 30 минут PASS; испытание 350 Вт INVALID, повтор отменён. После смены платформы первый T-MED сохранил M08 FAIL с причиной UNKNOWN, а полный повтор дал 10 PASS / 2 INFO, включая M08 PASS. Первый протокол не переписывался. Все подробные журналы испытаний остаются в приватном evidence.

## Служба после включения

Установка после 50 описана в [50, раздел 10](50_Сервисы_Gateway_MCP.md#10-проверка-после-включения). На новой сборке по lock RB-06 с ядром 146 передать установщику `--baseline-name baseline.json`. Новая версия установщика по умолчанию выбирает baseline.live-2026-10-18.json с F09 для платформы 147 с лимитом 300 Вт; установленная на живом сервере старая служба автоматически не меняется. После принятия новой платформы владельцем перейти на её эталон по [80](80_Восстановление_и_апгрейд.md#смена-платформы). На сервер переносится минимальная копия из коммита в /opt/ailab-acceptance/<commit12>/; current выбирает её атомарно. Служба enabled запускается автоматически после включения и готовности сервисов. T-MED при смене платформы выполняется вручную с разрешением владельца.

Проверить systemctl status ailab-postboot-check.service. Итоги каждого запуска находятся в ~/llm-gateway/logs/postboot/<UTC>_<boot8>/: healthcheck.out, сырой T-FAST, оценённый протокол и summary.json. Строка AILAB_POSTBOOT в журнале содержит result, health, tfast, known и known_resolved.

Сырые статусы остаются в tfast. tfast_effective меняет FAIL на KNOWN только когда все непройденные проверки перечислены в known-findings.json. Принята только F04.pi_image_requires_vision, OBS-10-01. Новая ошибка остаётся FAIL. Если известная проверка стала PASS, known_resolved сигналит исправление.

Приоритет: FAIL при непринятом FAIL/TEST_DEFECT, отсутствии готовности или health не 20/20; затем REVALIDATE; затем DRIFT; иначе PASS. KNOWN и INFO не повышают итог. Коды: неготовность 2, FAIL 1, REVALIDATE 3, PASS/DRIFT 0. Ошибочный код означает failed unit, enabled сохраняется.

Health-check RB-07.1 не проверяет ответ Q6. F05 INFO до первой загрузки Q6 после включения допустим. После загрузки профиль текущего ID даёт PASS; строки с чужим ID остаются FAIL. Выгрузка Q6 из памяти не удаляет записи профиля текущей загрузки.

## Принятое наблюдение повторных embedding

RB-10.1 ACCEPTED_WITH_LIMITATIONS, E1:39 запросов,99 сравнений строк. Пакетные ответы точны в 89/90 строк, первый после повторной загрузки embedding точен. Первые одиночные ответы точны, повторные могут отличаться. Максимум 0.0051, косинусное сходство не ниже 0.99943.

Решение приёмщика 2026-10-17: M05 остаётся точным сравнением первого ответа, допуск 0. Отличие повторного ответа на тот же текст записывается INFO с измеренными величинами и не является FAIL. Неизменённый оценщик численно сравнивает только первый ответ; INFO повторов отражается в сопровождающем отчёте. Кэш считается вероятной причиной, но не доказан; влияние ядра на частоту не исключено. Размер 4096 не заменяет точное сравнение.

## Уточнения ручной приёмки RB-13

F04 со статусом FAIL принимается как известное ограничение только если единственная непройденная проверка перечислена в [known-findings.json](artifacts/postboot/known-findings.json). Сейчас это F04.pi_image_requires_vision, OBS-10-01. Любая другая непройденная проверка требует остановки. Сохранить сырой FAIL и отдельно записать принятие известной находки; обычный оценщик не превращает её в PASS.

Установщик [40](40_Q6_runtime.md) подставляет текущий ID из API в wrapper. Выполнить разрешённый T-MED, получить решение владельца и создать новый вариант эталона по [80](80_Восстановление_и_апгрейд.md#смена-платформы). Исходные baseline не менять ради PASS.
