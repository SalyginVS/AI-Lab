# Рабочий процесс

## Роли

1. **Planner / Reviewer AI** — анализ, план, проверка рисков, подготовка материалов, review результатов. Конкретная модель выбирается по fit-for-purpose.
2. **Research AI / Web verification** — проверка актуальности внешних инструментов, версий, changelog, community signals. Используется только когда нужна свежесть фактов.
3. **Executor AI / Local models** — bounded execution по заранее заданному контракту. Не является автономным владельцем изменений.
4. **Vladimir** — выполняет команды, принимает решения, утверждает write-actions, коммитит и пушит AI-Lab documentation repo.
5. **AI-Lab Obsidian/GitHub** — единственный durable source-of-truth для паспортов, архитектуры, ADR, грабель и этапов.

## Source-of-truth rule

Канонический контур:

```text
/home/vladimir/llm/AI-Lab
git@github.com:SalyginVS/AI-Lab.git
```

Server runtime directories не являются Git/source-of-truth контуром. Сервер может содержать runtime-код, модели, systemd services, backups и конфиги, но durable knowledge фиксируется только в AI-Lab.

## Правила работы

- Пошагово: один подэтап за раз.
- Перед write-action: явно указать, какой файл/сервис будет изменён.
- Перед деплоем: аудит на соответствие live-серверу.
- Конфигурации: полные файлы, не фрагменты, если файл должен быть заменён.
- Каждый завершённый этап: `Результаты.md` + обновление паспорта/архитектуры при необходимости + ADR/грабли при необходимости.
- Новые Markdown-файлы создаются только после placement map.
- Placement map обязателен для документации:

```text
факт / изменение → существующий файл → раздел → действие → нужен ли новый файл
```

## Запрещённые паттерны

- Создавать случайные отчёты в vault без привязки к `Этапы/`, `Грабли/`, `Решения/`, `Конфиги/`, `Meta/`.
- Использовать server-side Git history как замену Obsidian/GitHub knowledge base.
- Пушить runtime repo вместо обновления AI-Lab documentation repo.
- Превращать bounded model lane в Agent без отдельного validation gate.

## Complex Bounded Executor contract — Qwen3.8 Flash-Next Q6 / Pi

Статус: mandatory operating rule после acceptance `Q6-EXEC-LEASEFLOW-v1` (2026-10-06).

### Роль

```text
Planner / Reviewer AI
  architecture / contract / external review

Qwen3.8 Q6 + Pi
  complex bounded engineering execution

Vladimir
  owner / approval / commit / push
```

Q6 не является автономным владельцем архитектуры и не принимает собственный результат.

### Перед постановкой задачи

До формирования execution contract обязательно восстановить:

- подтверждённые project facts;
- ADR;
- предыдущие acceptance tests;
- текущий runtime/harness baseline;
- релевантный empirical evidence.

Не заменять проверенное project-specific знание универсальным шаблоном.

### Форма задачи

Для серьёзной задачи использовать workspace contract:

```text
TASK.md
spec/*
existing source
public examples/tests
```

Execution contract должен явно содержать:

- конечный результат;
- baseline;
- source-of-truth;
- scope / allowed files;
- forbidden changes;
- invariants;
- acceptance gates;
- evidence format.

Архитектурные решения, уже принятые control plane, модель не перепроектирует.

### Self-review обязателен

Зелёные tests первой реализации не являются концом задачи.

Обязательный цикл:

```text
implementation
-> first-pass checkpoint
-> reread TASK/spec
-> inspect full diff
-> inspect module interactions
-> search edge cases/invariant violations
-> regression tests for real defects
-> root-cause repair
-> full gate rerun
-> final diff review
-> READY_FOR_REVIEW
```

Не сообщать модели ожидаемое число дефектов.

### Recovery

При harness/infrastructure failure:

1. не начинать реализацию заново;
2. сохранить current worktree/checkpoint;
3. восстановить execution environment;
4. продолжить из фактического состояния workspace;
5. first-pass evidence не перезаписывать.

### Acceptance

Модель может выдать только:

```text
READY_FOR_REVIEW
```

Финальный `ACCEPTED` выдаёт внешний reviewer/control plane после независимых checks.

### Harness preflight

Перед serious Q6 run обязателен preflight из:

`Конфиги/pi_qwen38_q6_long_context_harness.md`.

## Обслуживание комплекта сборки

После изменения живой системы запустить неизменённый collector принятой версии и сравнить результат с последним принятым bundle. Bundle хранить приватно. Каждое изменение классифицировать как отражённое, DRIFT, REVALIDATE или требующее решения.
Обновить манифест и затронутый runbook. Прогнать [набор RB-10](../Сборка/90_Acceptance_suite.md): T-FAST и разрешённый T-MED; F07 выполнять после каждого включения сервера. Изменение условий Q6 требует ревалидации по ADR-031. Baseline тестов не подгонять под живую систему.
Обновление паспорта означает выпуск новой версии паспорта. Прежний снимок сохранять с исторической пометкой. До публикации повторять [проверки комплекта](../Сборка/tests/repo/check_package.py), включая границу публичных данных.

При обслуживании запускать `python3 -I Сборка/tests/repo/check_package.py --start <последний принятый commit комплекта>` с необходимыми evidence. При другой базе публичного сравнения передать `--base <принятый базовый commit>`. Изменение принятых артефактов после --start даёт FAIL намеренно и требует отдельной приёмки. После squash/rebase передать существующий --start явно; предпочтительно сохранять историю через merge commit.
