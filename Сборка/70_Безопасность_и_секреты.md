# 70. Безопасность и секреты

Статус: кандидат RB-09, PARTIAL_NOT_ACCEPTED. Применение до закрытия gates запрещено.
Назначение: создать новые секреты и применить отдельно полученный приватный пакет на новой системе.
Порядок использования: параметры площадки, контроль целостности, приватная процедура, новые секреты, проверка.
Этот runbook не является разрешением менять действующую лабораторию.

## Место в сборке

После подготовки ОС по 10 получить и проверить приватный пакет.
Сеть, firewall и вход по SSH настроить по приватному пакету до сетевого запуска сервисов.
Секреты создать перед соответствующими операциями 50 и 60.
Проверки Ollama и Q6 по 20–40 выполнять с уже применённой защитой.
Повторить итоговую проверку после 50 и 60.
Согласованные настройки защиты определяются только приватным пакетом.

## Получение и проверка приватного пакета

LAB_PRIVATE_REPO задаёт владелец после создания отдельного приватного репозитория.
До этого используется локальный экземпляр, переданный владельцем отдельно.
Содержимое этого пакета не добавлять в рабочую копию AI-Lab.
История локального пакета сохраняется, remote в рамках RB-09 не создаётся.

На новой площадке, после появления репозитория владельца:

    umask 077
    git clone -- "$LAB_PRIVATE_REPO" "$LAB_PRIVATE_PACK"
    (
      cd -- "$LAB_PRIVATE_PACK"
      sha256sum -c SHA256SUMS
    )
    python3 -I "$LAB_PRIVATE_PACK/templates/render.py" --values "$LAB_PRIVATE_VALUES" --output "$LAB_PRIVATE_STAGING"

Ожидается: все хеши совпали, каталог staging создан заново, незаполненных маркеров нет.
При ошибке остановиться. Источник пакета и контрольный commit подтвердить у владельца отдельно.
SHA256 проверяет целостность, но сам по себе не подтверждает происхождение.
Значения площадки хранить в приватном LAB_PRIVATE_VALUES.
Копию с живыми значениями не публиковать.
Порядок применения и точные команды находятся в README.md приватного пакета.
Сначала проверить статус пакета и незакрытые ограничения.
Проверку конфигураций выполнять до их активации с доступной локальной консолью.
Проверки после применения проводить по приватной карте и runbooks 20–60.
При отказе использовать описанный в приватном пакете порядок восстановления.

## Реестр секретов

Пути с LAB_SERVICE_ROOT относятся к новой серверной установке.
Пути с LAB_CLIENT_HOME относятся к новому клиенту.
Права ниже задают цель при сборке.
Режимы действующей системы перечислены только в приватном evidence.
Значения не загружать в Git, review bundle или журналы.

| Имя | Назначение | Кто создаёт и когда | Путь и целевые права | Кто читает | Ротация и перезапуск |
|---|---|---|---|---|---|
| LLM_GATEWAY_TOKENS | Карта токенов клиентов Gateway | Владелец запускает генератор runbook 50 перед первым запуском | LAB_SERVICE_ROOT/llm-gateway/.env; 0600, владелец сервисов | Gateway; RAG использует первый элемент карты | Создать новую карту в новом приватном файле; обновить потребителей; атомарно заменить файл; перезапустить llm-gateway.service и rag-mcp.service; старые токены проверить на отказ |
| LLM_ORCHESTRATOR_TOKEN | Учётные данные оркестратора | Генератор 50 вместе с картой | Тот же файл; 0600 | Оркестратор и процессы, загружающие это окружение | Новый токен обязан входить в новую карту; заменить вместе с картой; перезапустить Gateway и потребителей оркестратора |
| secret_key SearXNG | Внутренний секрет SearXNG | Владелец через render.py из runbook 50 при новой сборке | LAB_SERVICE_ROOT/searxng/core-config/settings.yml; 0600, владелец контейнера по runbook 50 | SearXNG core | Сгенерировать новое значение и новый settings; заменить; пересоздать core по runbook 50; проверить работу |
| auth.json Pi | Хранилище ключей провайдеров Pi | Владелец по 60 при подключении провайдера | LAB_CLIENT_HOME/.pi/agent/auth.json; 0600, владелец клиента | Pi и расширение Pi | Изменить только запись нужного провайдера; для Gateway согласовать с новой картой; закрыть старую сессию Pi и перезапустить расширение; проверить новый доступ |
| SSH_CLIENT_PRIVATE_KEY | Идентичность нового клиента | Владелец генерирует на новом клиенте перед первым доступом | LAB_SSH_CLIENT_KEY внутри LAB_CLIENT_HOME/.ssh; 0600, каталог 0700 | SSH-клиент или агент владельца | Создать новую пару; добавить публичную часть на сервер; проверить отдельную сессию; отозвать старую публичную часть и выгрузить старый ключ из агента; сервер перезапускать не требуется |
| SSH_CLIENT_PASSPHRASE | Защита нового приватного ключа | Владелец при генерации пары | В памяти владельца или выбранном хранилище; в файлы проекта не записывается | Владелец и SSH-агент | Изменить фразу штатным ssh-keygen; перезагрузить ключ в агенте; активные сессии закрыть по решению владельца |
| SSH_HOST_PRIVATE_KEYS | Идентичность нового сервера | ОС и владелец при сборке сервера | /etc/ssh/ssh_host_*_key; 0600 root:root; публичные файлы не секреты | Служба SSH | Создать новые ключи; проверить конфигурацию по приватному пакету; перезапустить службу по его процедуре; подтвердить клиентам новые отпечатки |
| SSH_OPERATOR_PASSWORD | Вход и повышение полномочий оператора по принятой процедуре | Владелец при создании учётной записи | ОС хранит хеш в /etc/shadow; права задаёт пакет ОС, значения не читаются | Механизмы аутентификации ОС | Сменить штатной утилитой passwd интерактивно; не передавать аргументом команды; новые входы проверять отдельно; перезапуск служб обычно не нужен |

Публичные части SSH и authorized_keys не являются приватными ключами.
Доступ к ним на новой системе задаётся приватной процедурой.
Дополнительные учётные данные провайдера добавляются в этот реестр по имени до ввода в эксплуатацию.
Отсутствие чтения auth.json не доказывает отсутствие дополнительных провайдеров.
Неизученные входы и полнота реестра отражены статусом T6 в handoff.

## Создание и замена значений

Генератор runbook 50 создаёт новые токены и отказывается перезаписывать существующий файл.
Для ротации использовать новый приватный путь с umask 077.
Проверить структуру карты без вывода её содержимого.
Проверить, что токен оркестратора входит в карту.
Сначала подготовить новые значения у всех потребителей, затем переключить серверное окружение.
В окно переключения учитывать перезапуск RAG и активные сессии клиентов.
После проверки отозвать старые значения и удалить временные файлы по принятой процедуре.

Секрет SearXNG создаётся заново генератором настроек 50.
Изменения compose и повторный запуск описаны в 50.
Хранилище Pi создаётся с целевыми правами по 60.
Приватные ключи и исходные файлы секретов с живой системы не переносить.

## Новые ключи SSH

На новом сервере создать собственные ключи хоста штатным ssh-keygen.
Не переносить прежние приватные ключи.
Новый ключ хоста меняет отпечаток сервера.
Получить отпечаток через доверенный отдельный канал.
Только после сверки удалить устаревшую запись из known_hosts и записать новую.
Не отключать проверку ключа хоста для обхода несовпадения.

На новом клиенте создать новую пару и сохранить приватную часть с целевыми правами из реестра.
Публичную часть добавить в authorized_keys оператора по приватному пакету.
Проверить новый вход в отдельной сессии, сохраняя консольный доступ.
Конкретные настройки входа определяет приватный пакет.

## Контроль после сборки

Проверить целостность приватного пакета и соответствие сгенерированных файлов.
Проверить SSH штатной проверкой конфигурации и новой сессией.
Проверить firewall по приватному пакету.
Ночная проверка использует sudo без интерактивного ввода для чтения статуса UFW.
Соответствующее правило sudo задаёт приватный пакет.
Проверить его от оператора на новой системе до включения ночного расписания.
Проверить положительные и отрицательные сценарии токенов по 50 и 60.
Новые значения и сведения о защите сохранять только в приватном evidence.
